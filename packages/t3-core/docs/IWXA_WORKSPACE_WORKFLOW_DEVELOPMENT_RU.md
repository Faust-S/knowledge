# IWXA Workspace & Workflow: самостоятельная линия развития

**Решение владельца 26.11.2026:** развивать общую Workspace и Workflow как крупное самостоятельное функциональное направление IWXA. Не привязывать общую технологию к Advice Logistics, отдельному домену или интеграции конкретной программы. Это развитие действующего T3/Agent, не новый продукт, ядро, Store, Host, Graph, Task Engine, IAM, Router или формат обмена.

## 1. Исходная основа и владельцы

- Выпущенная T3 0.3.0: release/t3-0.3.0@fd927a1efb083219442d9504285f75fa738dbdda. Рабочая ветка work/2026-11-26-workspace-workflow-development начинается непосредственно от этой базы. Номер будущего выпуска общей технологии пока не назначен. Выпущенные T3, T4, Agent, Center и Publisher и рабочие линии Agent 0.6.5/0.6.6 не менять из этой линии.
- Канонический общий Workspace/Host/View State и модульные contributions остаются в packages/t3-core. Оригинальный Kernel/Store/Exchange сохраняется. Agent остаётся владельцем своего исполнения Task, Graph, ToolRuntime, DurableAutomation, Human Review и Result; предметные программы и домены остаются владельцами своих моделей, операций и данных. Не копировать Agent Graph в T3 для получения универсальной визуальной доски.
- **Решение владельца 27.11.2026 о последовательности выпуска Agent:** общая Workspace & Workflow продолжает разрабатываться в той же ветке и в полном объёме W01–W08, без сокращения функционала, изменения целей или потери истории. Новая Agent 0.6.6 выпускается отдельно. Внедрение этой функциональной линии в Agent перенесено на следующий выпуск после 0.6.6; предварительный номер 0.6.7. Это перенос интеграции, а не остановка или отсрочка разработки общей технологии.
- При фактическом начале интеграции определить последнюю принятую стабильную редакцию Agent на тот момент (не ниже выпущенной новой 0.6.6), зафиксировать её точный Git ref/commit и полный состав ранее принятого функционала. Интегрировать изменения поверх этой базы в отдельной продуктовой ветке, сохранив существующую ветку Workspace & Workflow и её историю. Не откатываться к 0.6.4/0.6.5, не заменять новые функции Agent прежними реализациями, не менять stable/release ветки. При расхождении исходников адаптировать contributions к оригинальным владельцам и контрактам принятой базы, а не подменять Agent общим Host. Проверить накопительную регрессию принятого функционала и целостный профессиональный Workflow. До фактической приёмки не объявлять 0.6.7 стабильной; номер предварительный.
- Исторические решения, исходные результаты испытаний и ссылки на коммиты сохраняются; это решение заменяет только прежнюю привязку внедрения к 0.6.6. Оно не активирует Project/Process production writes, не меняет D1/D4 и не утверждает новое хранилище.
- Corporate: только одна полная исходная подписанная Workspace компании, все данные работы сохраняются в ней, export/import всей Workspace с history/assets/relations/schemas. Личный/предметный обмен и междоменные проекции не заменяют этот контур. D1 authority и D7 entitlement проверяются оригинальными владельцами. Лицензия, доступный viewer, выбранный объект и граф не дают права выполнять действия.
- Объект деятельности, представление, методика, исполнительная Task и предметная модель различны. Свободное исследование допустимо без исполняемого Graph, Atlas, домена, установленной программы или обязательного шаблона. Визуальный порядок материалов не создаёт исполнительные зависимости.

## 2. Разработанные участки

### W01: стабильная идентичность и жизненный цикл сохранённых представлений

[eeaa952b](https://github.com/Faust-S/knowledge/commit/eeaa952b3d358f1e63fd5d3210749d00b9c48a2b). Развит original workspace-persisted-view-state, RichWorkspaceReadModel и workspace.view-state.save. Старые IDs сохраняются. Новый ID 128-bit random (WebCrypto), не вычисляется из названия. Unique normalized name сохраняет прежнее поведение обновления; неоднозначность требует явного выбора. Кнопка «Изменить» открывает исходный вид и фиксирует его baseRevision; переименование не меняет ID. Новое создание после удаления получает новую идентичность. Неизвестный outcome создания в текущей сессии использует тот же ID и сверяет видимый readback, не повторяет запись при совпадении. Старый 32-bit helper оставлен для совместимости, не применяется для создания в основном Rich Workspace. Не обещать глобальную уникальность названий при нескольких конкурентных клиентах; явное редактирование разрешает неоднозначность без молчаливого overwrite. Original owner CAS и существующая проверка полномочий не заменены.

### W02: сохраняемый состав материалов и режим профессионального вида

[66150d0b](https://github.com/Faust-S/knowledge/commit/66150d0b4345f77a54dfa8759ad9922873ca3010). Existing internal saved-view v1 дополнен optional presentation: version=1, mode, ordered selected refs (object_id + revision), detail ref. Это additive field существующего View State, не новый schema family, Asset, Store или формат .iwxa. Старые filter-only records не требуют миграции и сохраняют исходную форму. Сохранение локального вида и persistent view используют тот же capture. Scope/current revision сверяется по полученному текущим Host каталогу; нет копий payload, разрешений, скрытых действий или автоматической замены старой редакции. При обновлении объектов после открытия представления вычисляется новый read-only restore. Изменившиеся/недоступные материалы не попадают в выбранную композицию; виден счётчик, пользователь может принять доступный состав. Новый save не скрывает неполный состав. Сравнение сейчас штатное сравнение метаданных двух объектов, не готовый универсальный научный viewer. Лимит 256 относится только к этому сохранённому выбору; отказ явный, без усечения исходной Workspace.

**Совместимость:** новая реализация читает прежний v1. Старый клиент способен проигнорировать новый optional presentation и при обновлении прежнего объекта потерять его; downgrade-writing не квалифицирован и не должен объявляться безопасным. До выпуска проверить точную схему original Host/Kernel и штатный .iwxa, сохранение extended records при обмене с предыдущими поддерживаемыми редакциями, явную обработку неизвестных представлений, lifecycle и совместимость миграции. Не повышать статус до принятого продукта на основании допустимости поля в source validator.

### W03: многокомпонентное полотно существующих материалов

[ca5cd18c](https://github.com/Faust-S/knowledge/commit/ca5cd18c532631d2efde970d1fc15f9977a5cc48), [cc1a846d](https://github.com/Faust-S/knowledge/commit/cc1a846d3635791318603fc969a2d31430756719). В actual WorkspaceView / RichWorkspaceReadModel добавлен режим «Полотно», использующий существующие объекты, ViewerRegistry, HostViewer и профиль Workspace. Внутренний picker выбирает материалы из уже полученного оригинального каталога по ID/schema; можно добавлять из разных поисковых срезов, переставлять, удалять, выделять, переключать краткий/подробный вид, одну/две колонки и широкие панели. Компоновка хранится в existing optional presentation.canvas (columns, detailed, wide), порядок и точные редакции в selected, фокус в detail. Старые filter-only и W02 presentations читаются без миграции. Не сохранять payload, экземпляры компонентов, новые permissions, произвольные loaders или executor graph в View State.

Новые пользовательские изменения полотна также pin текущие редакции до сохранения. При изменении исходного объекта restored state исключает его из отображения, явно показывает неполноту. Принятие доступных материалов сохраняет оставшиеся refs pinned; перестановка/удаление не подменяют версии. Сложный сохранённый вид не может быть неявно перезаписан простым фильтром или иным layout с тем же названием: требуется «Изменить» с actual baseRevision; точный совпавший readback не делает лишнюю запись. Старый filter-only unique-name update сохранён.

Панели используют existing HostViewer resolve с current grantedOperations и activeCapabilities. Для detailed viewer обязательно доступен original kernel.t1.getObject и совместимый разрешённый viewer. Содержимое берётся из exact getObject, не из summary payload listObjects; checkCanvasMaterialDetail расширяет original identity check на revision/schema/version. Raw toggle в полотне запрещён, отсутствующий viewer использует original UnknownObjectPreview, не раскрывающий payload. Поздний read после удаления/смены панели игнорируется. Existing EditorRegistry намеренно не активируется из read-only UI, открытие исходного объекта использует original route. Редактирование предметного содержания через штатные owner/editor маршруты, не через layout. Автоматических бизнес-команд при выборе/перестановке нет. Прежний command preflight сохранён вне canvas, подготовленные команды не исполняются по неполному восстановленному выбору. Existing relation, catalog, history и domain functions остаются.

Исправлена потеря session composition при refreshObjects: RichWorkspaceReadModel сохраняет состояние на том же workspace/profile key, скрывает content/actions и не получает предыдущий каталог пока objectsState не ready. После подтверждённого каталога возвращает composition с проверкой revision. Page/picker — временные controls, не часть сохраняемой методики. До 256 selected refs, одновременно монтируется не более шести панелей, выбор не усечён; предел не является ограничением всей Workspace. Пока это управляемая многопанельная композиция, не произвольный координатный холст и не набор новых специализированных вычислительных viewers. Полный W03 требует real Host/DOM и .iwxa квалификации; взаимодействие предметных редакторов и инструментов развивается у соответствующих владельцев.

### W04: проектирование и повторное применение профессиональных методик

[W04.1 de7c67c6](https://github.com/Faust-S/knowledge/commit/de7c67c69cd8fe44bb638df9d2e7e6ee53112428), [W04.2 d9c80628](https://github.com/Faust-S/knowledge/commit/d9c80628595ff5e6d3c4fc3ce455c3cc85a8f79c). В действующем RichWorkspaceReadModel добавлена панель «Методика», совместимая с полотном; состояние черновика привязано к Workspace/profile/kernel и не теряется при скрытии панели/обновлении каталога. При смене контекста сбрасывается. Методика необязательна для свободной работы. Имя, цель, применимость, этапы, предполагаемый участник human/agent/program, инструкция, явно заданные предшественники, ссылки на выбранные материалы с точной редакцией. До 64 этапов и 256 материалов в одном черновике, без ограничения состава самой Workspace. Используются original normalizeProject, normalizeWork, previewProjectTemplate (IWXA_T2_PROJECT_TEMPLATE_PREVIEW_V1); проверяются scope, существование/редакция материала, уникальность, циклы и целостность предшественников. Структурные группы независимых этапов — не рассчитанное расписание; поддержанная здесь связь finish-to-start с нулевым lag не заменяет остальные возможности оригинальной Work-модели.

Повторное применение через существующий project template preview: вставка совместимого предпросмотра или кнопка «Новая работа по этой методике» из проверенной структуры. Новый project ID и производные work IDs, переназначенные зависимости; структурированные ссылки на материалы старой работы не переносятся, нет копии payload. Тексты и структура методики сохраняются как намерение пользователя; это не очистка любых сведений, которые пользователь самостоятельно вписал в текст. Старые материалы для новой работы выбираются явно. Нет нового exchange schema, шаблонного Store или второго Graph.

W04.2: inspectWorkspaceMethodMaterials (CURRENT/CHANGED/UNAVAILABLE) и analyseWorkspaceMethodMaterialImpact. По явно объявленным связям выделяются этапы, требующие проверки исходного материала, зависимые продолжения, этапы без объявленного изменения и непривязанные изменившиеся материалы. Изменение исходного материала блокирует прежний preview до явного обновления выбора. Не доказывает эквивалентность входов, сохранность результата, право запуска, возможность повторного использования результата или фактически выполненный пересчёт. Сами результат/исполнение остаются у original owners.

**Граница W04:** SOURCE_IMPLEMENTED_DRAFT_ONLY. Сохранение вида не сохраняет методику, методика пока в сессии. Original Project/Process source owner на текущем исходнике имеет QUALIFICATION_AND_D4_PENDING, writesAuthorized=false; immutable activation receipt и activation gate не закреплены. Выпущенный T3 0.3.0 не означает активации этого конкретного C3 owner. Нельзя поднимать флаг, синтезировать evidence или записывать методику через View State. Кроме того original normalizeProject/normalizeWork не сохраняют все semantics goal/actor/instruction/materialRefs из preview.parameters: до materialization нужна без потерь согласованная привязка к оригинальному source owner/relations/assets и проверенный readback. Затем точный C3 qualification, D4 dual-hash gate и post-binding qualification. Actor designation не является assignment, D1 authority, D7 entitlement или execution grant. Agent Graph/Task остаётся у Agent (product integration после выпуска новой 0.6.6, предварительно 0.6.7, поверх актуальной принятой stable-базы), TOOL допускает READ в просмотренном graph node config; native write идёт по исходному маршруту Task/ToolRuntime/approval. Нет запуска из preview, изменения Graph/Task или объявления W05 выполненным.

### W04.3–W04.4: без потерь через original Project/Work source owner

[W04.3 56a9e039](https://github.com/Faust-S/knowledge/commit/56a9e0395bf221d581d9b4947460e5030d872a62), [W04.4 d254a432](https://github.com/Faust-S/knowledge/commit/d254a4329a6319333cb51cd02fb3ee3ba8b65a08).

Выбран additive optional methodology version=1 в existing Project/Work source payload, не новая object family/Store или формат exchange. Project сохраняет objective, materialRefs, ordered workIds; Work сохраняет stepId, intendedActor, instruction, materialRefs. Оригинальные projectId/workId, templateRef, domainApplicability, dependencies, schedule и status сохраняют прежнее значение. При отсутствии methodology legacy normalizers не добавляют поле. Структурно проверяются собственные поля, пределы, идентичность, scope, distinct refs, actor и явное соответствие material pins Project/Work. Material refs в payload являются плановыми ссылками внутри scope; не доказательство текущего доступа, material existence при native execution, canonical-head membership или entitlement. Точный Host/D1 admission необходимо реализовать и проверить до production wiring. В исходном UI methodology остаётся draft, не подменять её View State.

prepareWorkspaceMethodSourceInputs формирует полные inputs original Project/Work и порядок создания с явными prerequisite, не новый persisted journal. Проект и этапы могут быть записаны через original owner в существующий OwnerWriteGateway. Existing #resolveRefs проверяет actual live canonical head/record identity, исключает tombstones и несогласованный scope, для methodology Work фиксирует exact project revision и exact predecessor recordIds. Проверка транзитивного замыкания обнаруживает отсутствующие/изменившиеся связи и логические циклы, включая цикл через предыдущую редакцию исходной Work. New owner revise запрещает молчаливую потерю methodology и перемещение существующей method Work в другой project. Existing history qualification дополнительно проверяет family/objectId и live source target, не только совпадение recordId. Старый owner/межверсионное редактирование и portable exchange остаются открытыми.

reconstructWorkspaceMethodDraft и readWorkspaceMethodFromSourceOwner восстанавливают полную методику из original owner.load: ровно declared planned unscheduled Work set, exact project/predecessor record refs, полный состав материалов и их исходные редакции, display order отдельно от dependency order. Отсутствующая Work, tombstone, другая редакция или наблюдённая конкурентная запись отклоняют readback; старые записи не подменяются. Повторное чтение фиксирует наблюдённое изменение; это optimistic revision-set readback, не атомарный snapshot и не результат выполнения. Active/scheduled work нельзя молча превращать в редактируемый draft.

createWorkspaceMethodThroughSourceOwner использует только существующие create/load/history. Принимает явные стабильные recordIds и исходный knowledgeAt, immutable подготовленные inputs; до записи проверяет отсутствие конфликтов во всём составе. Создание в prerequisite order; exact readback сопоставляет canonical payload, ID, revision=1, original time и references. Потерянный ACK восстанавливается только при фактическом exact readback. Прерванное создание оставляет original partial history; возобновление по тем же inputs/IDs дописывает только отсутствующие этапы. Уже сохранённое не перезаписывается; другая цель/ID/time, прежняя история с tombstone, stale catalog или несогласованная запись блокируют повтор. Не создаётся новая очередь/исполнитель, не производится автоматический retry, rollback или revise. Это не атомарная multi-record transaction. Перенос exact creation identity через cold restart и штатное UI save требуют original activated owner/Host path; текущий черновой UI ещё не предоставляет этот маршрут. Source owner gate и release 0.3.0 не изменены.
