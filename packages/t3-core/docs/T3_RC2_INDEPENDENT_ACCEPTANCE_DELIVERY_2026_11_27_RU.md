edc97212c0ee6111dee2c8e6cc2f0d4211068d11.

## Полученная независимая приёмка

По представленному владельцем отчёту Codex:
- NOT_ACCEPTED: квалифицированный Host не был запущен в доступном браузеру origin.
- Commit, опубликованные SHA-256 ZIP и манифеста совпали; проверяющий
  не скачивал архив и не пересчитывал хеш его байтов локально.
- Браузер сообщил NVIDIA Blackwell, vendor=nvidia, isFallbackAdapter=false,
  запрос WebGPU device успешен. Это сообщение проверяющего, а не новый
  аппаратный прогон из CI. Реальный инференс T3 не запускался.
- Все пользовательские сценарии BLOCKED; воспроизводимого дефекта продукта нет.
- Не считать отсутствие Host отсутствием GPU и не объявлять ACCEPTED.

## Граница решения

Предыдущая передача предоставила reusable platform inputs, а не запущенный
сайт. Исправляется доставка, а не оригинальная архитектура.
[Подготовка](https://github.com/Faust-S/knowledge/commit/ab09d65a10b1a361a39e8b7ff825281cc393a070)
использует точный публичный release ZIP
c142597c759d6689c0298d0ec6abc7ee66b2eefbb1d5abb086efff6f0dea891e.
Существующие materializeIntegrationHost, registerT3LocalInferenceService,
materializeDomainMode и assertQualifiedKernelArtifact из этого ZIP
формируют один полный dist для выбранного HTTPS origin. Compiled assets
и нормативные Kernel bytes проверяются побайтно. Это не новый продуктовый Host.

На Windows доставка включает локальную статическую HTTPS-раздачу,
официальный Node.js x64 и START.cmd. Запуск не устанавливает npm-пакеты
и не компилирует исходники. Модели, закрытый код, личные данные,
ключи подписи и TLS private key в архив не включаются.
Создаётся короткоживущий localhost TLS server certificate при запуске,
доверие CurrentUser Root только после явного согласия; удаляется при
нормальном завершении. При аварийном завершении следовать README.
Не отключать проверку сертификатов в независимой приёмке.

## Квалификация доставки

Первый [Windows-прогон 45987367299](https://github.com/Faust-S/knowledge/actions/runs/45987367299)
подтвердил скачанный ZIP, неизменные compiled assets и Kernel, собрал 97
записей offline manifest; реально запустил локальный HTTPS с проверкой
сертификата в Node HTTPS client; браузер открыл оригинальный Workspace
и BLI, создал два объекта, связь, вложение и штатный .iwxa. Остановился
на ожидании автономного режима в браузере с page-only TLS exception.
Не засчитывать offline PASS и не публиковать непроверенный комплект.
В редакции 0cb276420708c8942023e1d1528dfdffc60b2e5b повторная проверка
использует нормальное доверие временному сертификату на disposable
Windows runner, без отключения TLS в браузере, с диагностикой исходного UI.
[Повторный прогон 45987764329](https://github.com/Faust-S/knowledge/actions/runs/45987764329).
Фактические итоговые результаты сверять по Actions и release assets,
не считать этот документ свидетельством завершения этого прогона.

## Как реально открыть

Локальный путь: открыть комплект с START.cmd на машине, где работает
проверяющий браузер. Адрес https://localhost:18443/workspace/.
Браузер в другой виртуальной машине не разделяет localhost компьютера владельца.
Передавать Codex адрес только после реального запуска и подтверждения доступности.
Встроенный браузер должен проверять UI; терминал может подготовить
файлы и запустить статическую раздачу, но не управлять браузером.

Если Codex работает в удалённой среде без доступа к этому loopback,
нужен отдельный доступный HTTPS origin. На момент подготовки
Faust-S/knowledge, Faust-S/Center и Br-test не имеют GitHub Pages,
отдельный корневой Faust-S.github.io не найден.
Нельзя использовать project Pages /knowledge/ как подстановку корня:
оригинальные маршруты /workspace/, /_iwxa/ и Service Worker закреплены за origin.
Нельзя самовольно заменить действующий сайт или настраивать публичный туннель.

Для явно предоставленного выделенного тестового HTTPS origin:
1. Checkout delivery commit 0cb276420708c8942023e1d1528dfdffc60b2e5b.
2. Скачать опубликованный platform-inputs.zip rc.2.
3. С Node.js и системным unzip (Windows tar.exe) из корня checkout выполнить:
   `node packages/t3-core/scripts/prepare-t3-rc2-acceptance.mjs /absolute/path/platform-inputs.zip /absolute/new/output https://actual-test-host.example`
   Здесь actual-test-host.example — только условный пример; заменить точным
   реально предоставленным origin без пути и завершающего слеша.
4. Разместить только output/dist в корне этого HTTPS-хоста. Не публиковать
   launcher, сертификат, examples или внешние receipts как файлы сайта.
   Раздавать .mjs/.js как JavaScript, .json как JSON, .wasm как WebAssembly,
   сохранять каталожные index.html и не добавлять SPA fallback.
5. Проверить HTTP 200, контрольные суммы runtime.js и t3-offline-manifest.json
   из receipt. Открыть /workspace/ встроенным браузером Codex.
   Если origin доступен только внутри отдельной сети, это остаётся блокером доступа.

## Приёмка без искусственных заданий

В generic Host не вводить дополнительный редактор предметной области только
ради теста. Для документа и вложения использовать example .iwxa,
действительно экспортированный оригинальным Kernel; открыть через штатный
Exchange. Для нового результата использовать оригинальный BLI и Human review.
Проверка offline сайта должна исключать сетевой доступ к сайту, а не только
внешний интернет при доступном localhost. Отдельно проверить холодное
открытие модели и генерацию без внешних сетевых запросов.
После запуска и подтверждения доступности продолжить ранее выданный
план независимой приёмки: реальный UI, физический WebGPU, consent,
редактирование и сохранение, offline restart и новый результат.
Не присваивать T3_READY по этому стенду. Домены и закрытые Actions не изменены.
