# Единый T3 в самодостаточных хостинговых сборках доменов

**Решение владельца: 18.11.2026. Область: все D01–D11 и будущие веб-домены IWXA.**

Нормативный смысл: [карта кодового владения и правило одного репозитория](https://github.com/Faust-S/iwxa/blob/knowledge/2026-10-02-system-atlas/knowledge/system/DOMAIN_CODE_OWNERSHIP_RU.md). Этот документ конкретизирует доставку существующего T3; не создаёт новый Host, Kernel, Store, Exchange, Factory, подписанта или пакетный формат.

## Релизная граница

**Для размещения сайта на хостинге достаточно только его веб-репозитория и стандартной среды сборки.** Например, для D10 — `Faust-S/artbazi.ru`, без обязательного клонирования `Faust-S/artbazi`, `Faust-S/T2`, `Faust-S/T3` или `Faust-S/knowledge`. Это относится к `build`, `build:site`, `dist/`, повторной сборке из чистого checkout, CI хостинга и аварийному восстановлению выпуска. Нормальные зависимости по фиксированному package lock допустимы; git-зависимости на IWXA-репозитории и скрытая загрузка исходников недопустимы.

| Момент | Канонический источник | Где берутся байты в итоговом сайте |
| --- | --- | --- |
| Разработка единого T3 | `packages/t3-core` этого репозитория | У сайта нет живой runtime-зависимости от места разработки |
| Явное повышение версии T3 домена | Принятый, хешированный выпуск оригинального T3 | Проверенные бинарные/статические артефакты и нужные контракты фиксируются **в веб-репозитории** |
| Повторная сборка сайта | Только checkout веб-репозитория | Из локальной версии артефактов T3, локальной проекции предметной логики и locked dependencies |
| Хостинг и браузер пользователя | Только единый `dist/` на origin сайта | Один T3, включая унаследованный T2, Workspace, Host/Kernel/Exchange/Lifecycle и разрешённые возможности T3 |

Не сохранять в веб-репозитории второй независимо развиваемый исходный Kernel. Транспортировать только оригинальные принятые компоненты и идентичность выпуска: `source SHA`, `version/contract`, SHA-256 файлов/манифеста, список компонентов и свидетельство совместимости. Проверять контрольные суммы при сборке. Для изменения предметной семантики обновлять канонического владельца без веб-суффикса и явно синхронизировать исполняемую проекцию в сайт с указанием обеих ревизий.

Перенос `packages/t3-core` в любой другой канонический Git-репозиторий — изменение **места разработки и процедуры обновления**, а не миграция уже собранных сайтов. Не закреплять URL `knowledge` как runtime API, git dependency или обязательный builder checkout.

## Требования к внедрению в конкретный домен

1. Зафиксировать baseline T2 и исходные проверки, не ломать рабочую версию. Для ещё не обновлённого домена действующий T2 pin и его builder допустимы как **переходное** поведение.
2. Создать для T3 в том же веб-репозитории версионированный набор принятых статических/исполняемых артефактов; регистрировать происхождение и SHA. Не вводить второй Kernel/Host/Store или самостоятельную T3-программу.
3. Создать/обновить собственный site builder, который на чистом checkout сайта с установленными locked dependencies **не обращается к другим IWXA-репозиториям** и даёт единый завершённый `dist/`, включая PWA/offline только там, где гарантирован корректный полный набор ресурсов.
4. Сверить все пользовательские маршруты и интерактивные действия, реальные Task/Result, сохранение и холодное чтение Workspace, независимый Exchange `.iwxa`, светлую/тёмную тему, мобильный экран и доступность. Проверить, что нет второго работающего слоя T2 после успешного перехода.
5. Разделять build/source PASS, браузерный PASS, подлинную установленную/подписанную приёмку и производственный релиз. Не объявлять T3 или домен готовыми до доказательства необходимых продуктовых маршрутов.

## CI / GitHub Actions

По явному поручению в **публичном `Faust-S/knowledge`** можно запускать матрицы проверки закрытых доменов через ограниченный read-only Actions Secret (например, `DOMEN` для тех репозиториев, к которым ему действительно дан доступ). При этом CI может временно прочитать исходники выбранного домена **для проверки**; такое чтение не должно становиться зависимостью его обычной хостинговой сборки от `knowledge`. Не запускать Actions в приватных репозиториях.

- Только доверенные ветки/точные SHA и управляемые триггеры; не передавать секрет в PR из форков, недоверенные сборочные скрипты или `pull_request_target`.
- Нельзя печатать токены, приватный исходный текст, чувствительные файлы, содержимое `dist/` или загружать их как публичные artifacts; публиковать только минимальные статусы PASS/FAIL и обезличенную диагностику.
- Чтобы проверять другие домены, read-only токен должен иметь явный доступ к каждому выбранному приватному веб-репозиторию; наличие доступа к D10 ничего не доказывает для D01–D09/D11.
- `Faust-S/T2` и `Faust-S/T3` остаются существующими владельцами прежних исходников/оригинальных owner-процессов, но **не обязательными репозиториями для обычной сборки** уже переведённого на T3 сайта.

**Не является уже реализованной миграцией:** эта политика не означает, что прежние T2 сборщики перестали клонировать T2, или что каждый домен уже содержит полный T3. Реализацию и доказательства оформлять для каждой продуктовой ветки отдельно.
