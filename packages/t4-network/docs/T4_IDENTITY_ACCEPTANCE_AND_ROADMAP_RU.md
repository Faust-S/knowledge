# T4 Identity & Infrastructure: дорожная карта и программа испытаний

Редакция 0.1, 26.11.2026. Все новые испытания имеют статус NOT_RUN.
См. [архитектуру](T4_IDENTITY_AND_DOMAIN_INFRASTRUCTURE_RU.md) и [стенд](T4_SELF_HOSTED_IDENTITY_PILOT_RU.md).

## 1. Этапы и критерии перехода

| Этап | Результат | Условие перехода |
|---|---|---|
| I0 | Зафиксированная исходная композиция T4 RC и проект | исходники, точная ревизия, границы, согласование владельцем стенда |
| I1 | P0: оригинальный T4 между двумя физическими устройствами | настоящий TLS/WebDAV/peer, original Kernel/Access/Vault, одна Workspace, readback и отказ/возобновление |
| I2 | IWXA ID TEST | Keycloak, TLS, два клиента и API с разными audience, регистрация/вход/выход, recovery; локальный T3 независим |
| I3 | Связь с оригинальной личностью | dual proof, неизменный actor, атомарный штатный readback, отказ конфликтов, два устройства с разными ключами |
| I4 | Два предметных домена | реальный Host + оригинальный IAM, независимые данные; один SSO, раздельные membership/Workspace; отсутствие прав не обходится |
| I5 | Междоменный рабочий процесс | разрешённый Task → исполнение → Result → review/apply; восстановление и отсутствие повторной мутации |
| I6 | Agent Desktop/Mobile, перенос узла и эксплуатация | нативный вход, локальная автономность, перенос/восстановление, отзыв, измерение ресурсов и RTO/RPO |
| I7 | Независимая приёмка | точный commit/build, реальные устройства, журнал доказательств, регрессия, решение владельца; production отдельным допуском |

Не менять релизный scope 0.1 RC. Подготовку I2 можно начать в отдельной ветке параллельно I1, но I2 не является предпосылкой использования T4 и I4/I5 не принимаются раньше I1/I3. Не активировать тестовый режим в production. Исторические PASS исходных тестов не переносятся на новую композицию.

## 2. Распределение разработки

- Faust-S/knowledge/packages/t4-network: исходные network profile/topology/placement/transport, документация, проверяемые интеграционные сценарии.
- Faust-S/knowledge/packages/t3-core: только каноническая интеграция внешнего доказательства с существующим Access/Registry/Vault и допустимыми Host context. Изменять оригинальные контракты только при реальной необходимости и с регрессией. Не создавать второй IAM. Проверить владельца private upstream перед синхронизацией; не копировать закрытый код в открытый репозиторий.
- Admin Center: штатный допуск сотрудника/организации, оригинальные GRANT/STATUS и enrollment; Publisher: штатные лицензии, не зависящие от SSO как подмены прав.
- MarketOps/ArtBazi: предметная логика в предметном owning repo; сайт, UX и интеграция T3/T4 в репозитории сайта, с одним конечным dist на домен. Сначала один домен, затем второй.
- Personal Agent/Mobile: встроить вход в существующий интерфейс учётного подключения, локальная работа остаётся основной; выбрать Workspace/организацию и устройства без технической перегрузки.
- Infrastructure TEST: после уточнения ОС и сетевого режима создать deployment manifest в согласованном месте. Секреты и персональная топология только локально.

Пользовательский UX: «Войти в IWXA», «Продолжить локально», «Подключить устройство», «Подключить рабочее пространство», «Отключить сеть», «Выйти из IWXA». В сетевых ошибках показывать действие и результат, не raw claims, ключи или HTTP dumps. Указать разницу между входом, выбором организации, разрешением на передачу и завершением синхронизации. Вход не должен блокировать редактор и создание личного Workspace.

Все ниже NOT_RUN. Для каждого сценария хранить commit, build, среду/устройство, входные refs, проверенные действия, исходные Object/Event/Task/Result или receipt readback, ожидаемый/фактический исход, время и причину блокировки; обезличить вывод.

| ID | Сценарий | Критерий PASS |
|---|---|---|
| P01 | Два физических устройства и SELF_HOSTED | настоящий TLS/WebDAV + аутентифицированный peer; независимые Vault/Kernel, один write owner |
| P02 | Обычный LOCAL_T3 при отключении всего стенда | создание/изменение личного объекта, локальная модель при наличии, штатное чтение без IdP |
| P03 | Запись и чтение T4 | оригинальная разрешённая мутация и readback получателя; реплика не становится owner |
| P04 | Остановка сети/Host после отправки, до подтверждения | штатный recovery; нет повторной предметной мутации или недопустимой повторной подписи |
| P05 | Multipart при поддержанном профиле | реальный большой Asset, байты/хеш совпадают; unsupported payload остановлен до изменения subject |
| P06 | Недействительный TLS/peer/endpoint | сетевой отказ без передачи или применения |

| A02 | SSO A→B в том же браузере | нет повторного ввода пароля при действующем сеансе и допустимой политике; отдельный client/API audience |
| A03 | Отказ токена другого API/issuer/TEST | домен отвергает неверные issuer, signature, audience, expired, ID-token-as-access-token; ноль subject writes |
| A04 | Callback protection | чужой state/nonce, неверный PKCE, незарегистрированный redirect и replay code отвергнуты |
| A05 | Выход и ротация IdP signing key | закрытие сессий по политике, измеренный предел оставшегося токена; JWKS rotation работает; неизвестный ключ без проверки не принят |
| A06 | Блокировка IdP аккаунта | новые сетевые входы/операции согласно freshness policy прекращены; не заявлять мгновенный отзыв уже выданных offline tokens |

| B05 | Отвязка/перепривязка | требуется подтверждённый штатный процесс; нельзя получить старый actor чужим IdP-сеансом |

## 4. Порядок проверок и независимая приёмка

Самостоятельная адресная проверка доступными инструментами после каждой существенной группы изменений; накопительные тесты пакетно при переходе I-stage, не запускать очередь Actions на каждый документационный commit. CI только там, где владелец разрешил; закрытый код не выносить в открытые Actions и артефакты. Использовать оригинальные Node/Python checks и штатные qualification маршруты; fixture не заменяет реальный Kernel. Codex использовать для недоступных операций и независимой финальной приёмки; для проверки UI использовать встроенный браузер Codex, не Chromium/Playwright/Puppeteer; установленный нативный Windows проверять на допущенной среде владельца/Center согласно действующим ограничениям.

Отчёт содержит отдельно SOURCE_CHECK, CONTRACT_TESTS, NATIVE_KERNEL, REAL_TWO_DEVICE, IDP_SSO, DOMAIN_ISOLATION, CROSS_DOMAIN, OFFLINE, RECOVERY, INDEPENDENT_ACCEPTANCE. PASS допускается только при доказательстве конкретной ревизии и среды. BLOCKED/NOT_RUN не превращать в PASS. Не присваивать T4_READY, PRODUCTION_READY или PRODUCT_ACCEPTED по регистрации учётной записи или по числу unit tests.

Предлагаемый минимальный порядок запуска: I1 реальная сеть; I2 identity server; I3 original binding; I4 один домен, затем второй; I5 прикладной маршрут; I6 desktop/mobile и перенос. Открытые вопросы: точная ОС/ресурсы мини-ПК, TLS/DNS, фактический native Host для доменов, допустимое оригинальное представление связи issuer/sub→actor и продуктовый corporate gate. Всё это проверяется до реализации соответствующей группы.
