# IWXA Activity 0.4. План и первая реализация

База: release/0.3, bccd0fad3a1c97270b242ccb4c5e7ce7ec4183f3, установленная квалификация 45197570949. Релизную ветку не изменять.

## Целевой маршрут

Домен -> разрешённые факты и модели -> восстановление внешним инструментом -> Activity: группировка, проверка смысла и применимости, обезличивание -> оригинальный IWXA Exchange -> адаптация и фактический Result получателя. Agent координирует подключённые инструменты. Atlas планирует конкретные Work. Не создавать ещё один графовый движок, Task Engine, IAM, Store, Core, Router, редактор BPMN, симулятор или формат .iwxa.

## Последовательность

- A4.1: локальное сравнение исходных моделей D05 и затем штатный доменный readback. Модели и исполнения не смешивать. В первой итерации использовать только существующий operation-route; схема данных определяется доменом.
- A4.2: приём результатов Rust4PM/Propel через действующие Agent ToolProviderPort и артефакты Workspace. Полная траектория/варианты, объектные связи, эпистемические статусы. Не использовать анонимные алиасы разных выборок как общую семантику.
- A4.3: переносимая технология с областью применимости, существенными требованиями, входами, выходами, ролями, критериями приёмки, различиями вариантов и ссылками на доказательства в исходной среде. Подтверждение предметным владельцем; стандартные BPMN/DMN через оригинальные инструменты Agent.
- A4.4: квалифицировать ARX для табличных обобщений, Presidio для текстов, OpenDP для допустимой агрегированной статистики. Проверить риск связывания графа и повторных публикаций. Измерять полезность обобщения и проверять полномочия отдельно.
- A4.5: принимать воспроизводимые результаты Mesa/SimPy/SIMOD/Prosimos из Agent, сохранять происхождение и модельный статус. Не считать модель исполнением.
- A4.6: использовать оригинальный Exchange T2/T3 для подтверждённого предметного профиля технологии. Не вводить новый формат или экспорт на основании одного UI-флага.
- A4.7: независимый импорт, адаптация получателем, планирование через Atlas при необходимости, исполнение доменом.
- A4.8: оценка фактической полезности (качество, затраты, длительность, повторное применение) с сопоставимыми базой и результатом.

## A4.1-I. Локальная группировка нормативных моделей

Семантика маршрутов сверена с разрешённым источником D05 (без публикации приватных исходников). Программа принимает существующий объект калькулятора operation-route или локальную копию его исходного Kernel Result. Это не доказательство полномочий, подписи, актуальной Workspace или физического исполнения.

Раздел «Группировка маршрутов» в «Реконструкция»: до 24 отдельных JSON-файлов общим объёмом до 8 МБ; 128 операций, 1024 зависимости на маршрут. Встроенные модели для первого запуска обозначены примером. Все вычисления происходят локально в существующем Activity; сырые записи не сохраняются. При смене раздела выборка очищается.

Группировка: точное название/тип, признак параллельности, контрольная веха, полный набор прямых зависимостей. Смена исходных ID и порядок записей не меняют группу; повторяющиеся смысловые пары требуют ручного сопоставления. Один ID маршрута не может увеличивать число моделей через разные редакции. Длительность, ресурсы, материалы, примечания и параметры маршрута сравниваются отдельно; индивидуальные значения не копируются в результат. Отсутствующие параметры явно отмечаются. Названия операций остаются в частной локальной карточке, поэтому внешняя передача запрещена.

Количество моделей не является числом независимых хозяйственных исполнений; равенство структуры не устанавливает эквивалентность технологии или пригодность к повторному использованию. A4.1-I не изменяет оригинальный D2, A2, T3 grants или IWXA Exchange.

Критерий текущего шага: тесты независимости ID, разных названий и связей, повторных редакций, циклов, конфликта форматов, несовпадений параметров, отсутствия экспорта; TypeScript, исходная квалификация на Windows/Linux, установленное Tauri и старые маршруты. Дальше: квалификация чтения настоящих сохранённых моделей D05 через разрешённый источник и сопряжение с Agent.

## A4.1-II. Точка вызова для параллельной разработки Agent

Опциональная локальная точка входа: tools/activity-d05-route-review.mjs. Не является отдельным приложением, механизмом обмена или программным владельцем Workspace. При наличии квалифицированной Node.js среды адаптер оригинального ToolProviderPort может вызвать Node с этим точным скриптом без shell, передав через stdin JSON-массив уже разрешённых существующих моделей operation-route (до 8 МБ). Аргументы пути/команды не принимаются. stdout содержит единственный JSON локального результата либо типизированный HOLD с кодом, без исходных ошибок/путей. Процесс не читает Kernel, сеть и файлы.

Результат совпадает с вычислением нативного интерфейса. Он содержит названия операций, поэтому остаётся локальным артефактом разрешённой Workspace; не передавать его внешней LLM или другой организации, не записывать исходные данные в журнал. Сохранять через оригинальный механизм артефактов Agent, при больших результатах возвращать проверенную ссылку и digest, а не весь ответ. Зарегистрировать доступную операцию после проверки установленной Node.js и пакета скрипта с зависимостями. Не считать автоматически подключённой к Agent до исполнения через действующий ToolProviderPort, Task/Result и Human Review. Выходной код 0 означает успешную локальную группировку, 2 - HOLD; ни один код не разрешает экспорт.

### A4.3-I/II. Кандидат и связанные варианты

Использован прежний reviewD05RouteModelsWithQuality; обычный результат не расширяет выдачу частных значений. Явная includeTechnologyDraft:true формирует дополнительный локальный technology_draft. Контрольные точки сравниваются по полному исходному объявлению, с учётом кратности повторений; отсутствующая или неполная карта не заменяется проверками другого варианта. Смена профиля не образует новых комбинаций параметров.

Индивидуальные даты, названия заказов, документы, заметки и частные идентификаторы в локальный кандидат не копируются как норматив: сохраняется требование предметного уточнения их смысла. Исходные названия ресурсов и объявленные технические критерии присутствуют только в явно запрошенной частной рабочей области. Не подавать этот черновик внешней LLM и не передавать получателю.

В оригинальном доверенном Host параметр includeD05TechnologyDraft:true разрешает дополнительное локальное представление только совместно с enableD05RouteReview:true и includeD05QualityPlans:true. По умолчанию false. Он не создаёт право; доступ к исходным моделям остаётся через действующую subject binding. Узкий port не изменён. После смены Workspace, источника или отзыва старый результат сбрасывается. Никакого нового хранилища.

### A4.3-III. Предложение специалиста

В существующем разделе «Группировка маршрутов» пользователь открывает технологический кандидат, выбирает один исходный вариант, рассматривает условия и карту качества. Функция prepareD05TechnologyProposal подготавливает локальное предложение: назначение, входы, выходы, применимость, правила адаптации, требования к функциональным ролям, оборудованию и материалам, уточнение исключённого контекста. Каждая операция сохраняет исходные зависимости, параллельность, вехи. Каждая проверка сохраняет заявленные ограничения и действие при отклонении; функциональная роль предложена пользователем отдельно. Предложения разных моделей независимы. Отсутствующие значения не заменяются автоматически. PROPOSAL_NEEDS_INPUT, PROPOSAL_WITH_SOURCE_GAPS, PROPOSAL_FOR_DOMAIN_REVIEW различают заполнение формы и нерешённые требования. Ни один статус не является предметной приёмкой или доказательством анонимности.

### A4.3-IV. Подготовка к обезличиванию

Функция prepareD05DisclosureCandidate использует тот же выбранный профиль и пользовательское предложение. Для каждого заявленного параметра маршрута и операции пользователь явно выбирает RETAIN_DECLARATION (известное исходное значение) или PARAMETERIZE (правило адаптации для получателя). При параметризации исходное индивидуальное значение не копируется. Неизвестное значение не становится нулём; решение без правила остаётся незавершённым. Не разрешено автоматически удалять критерии приёмки, контрольные зависимости или блокировку выпуска. Названия исполнителей и оборудования заменяются предложенными функциональными требованиями; источник не меняется. Из кандидата выделяется полный детерминированный перечень текстовых полей для проверки внешними инструментами.

Это внутренний локальный результат, не новый формат обмена и не разрешение внешнего раскрытия. Условия применения и решение о выпуске остаются отдельными. Формы пока живут в текущей выборке, без подмены оригинального Task/Result и без фиктивного «сохранено». Принятый результат сохранять позднее через штатный Task и артефакты Agent или согласованный существующий предметный профиль IWXA Standard.

### Точка интеграции Agent

Сохранён tools/activity-d05-route-review.mjs. Без аргументов — прежнее сравнение исходного массива. Разрешённые отдельные флаги:
- --technology-draft: stdin — тот же массив оригинальных локальных Result с relations, stdout — локальный review с technology_draft.
- --technology-proposal: stdin JSON {records, group_id, model_number, proposal}; программа заново вычисляет черновик из records, а затем предложение, не принимает самопровозглашённый проверенный review.
- --disclosure-candidate: то же с обязательным parameter_decisions. Результат — локальный кандидат для дальнейшего предметного и текстового рассмотрения.

Это входы операций существующего ToolProviderPort, не формат обмена IWXA. Вызов без shell и без произвольного пути/команды. Лимит 8 МБ, результат 0 или типизированный HOLD 2. В исходном Agent (ветка work/2026-11-24-agent-process-modeling, 3b431260f3709ba0ed46d35556d124c39f9f37ab) сохранять механизм подтверждённого Task source, plan binding, digest и ProgramResultExecutionCell, аналогично оригинальному runtime/r4pm_program.py. Входы и частные результаты хранить в разрешённой локальной Workspace, не в аргументах shell или контексте внешней LLM. Реальное подключение адаптера в Agent и восстановление артефакта ещё не квалифицированы.

## A4.4-I. Первый внешний инструмент проверки раскрытия

Выбран оригинальный Presidio Analyzer 2.2.366 (27.10.2026, опубликован data-privacy-stack/presidio, source commit 211afc337241aee8bf495f282e83ef639a5d015f, MIT), с установленными оригинальными моделями spaCy en_core_web_sm и ru_core_news_sm 3.8.0. Ссылки: https://pypi.org/project/presidio-analyzer/2.2.366/ и https://github.com/data-privacy-stack/presidio/tree/211afc337241aee8bf495f282e83ef639a5d015f . Квалифицируем точные версии, не объявляем полноту распознавания русского языка.

Локальный worker tools/activity-presidio-scan.py запускает оригинальные AnalyzerEngine, SpacyNlpEngine и исходные Spacy/Email/Phone/IP/URL/IBAN/Date recognizers. Используется установленный язык en или ru, без автоматической загрузки моделей, без удалённого сервиса. tldextract настроен на пакетный локальный snapshot. Вход: полный результат --disclosure-candidate через stdin; worker независимо пересчитывает инвентаризацию, проверяет её полноту, запускает обработку каждого поля, возвращает позиции Unicode code point и оценки распознавателя без найденных строк. Результат привязан к исходным байтам, хэшу канонической technology и полному текстовому перечню. Профили имеют явно перечисленный ограниченный набор сущностей, score_threshold=0.3; это screening, не гарантия обнаружения всех ПДн, коммерческой тайны или уникальности процесса.

В существующей панели подготовки Activity предусмотрен приём локального результата Presidio для именно текущей редакции, отдельный просмотр en/ru, перечень полей и конкретных обнаружений. Изменение предложения делает предыдущий результат неприменимым; ручная правка и повторный прогон через Agent. Не суммировать находки разных профилей как уникальных лиц. Не удалять автоматически технический смысл. Внешний вызов из установленного Agent ещё требуется подключить штатным способом. Публичная CI квалифицирует оригинальные колёса и языковые модели на открытом модельном примере, отдельно от структурных тестов. Не заявлять PASS до фактического результата presidio-upstream-interop.

Далее: завершить квалификацию установленной Windows версии, закрепить оригинальную цепочку Agent Task -> кандидат -> Presidio -> проверенный результат -> Activity; затем ARX на табличных обобщениях и проверка редких траекторий/связывания, OpenDP только для подходящих агрегатов. Совместно с доменом проверить полезность обобщения, сохранность предметных ограничений и независимую адаптацию. Exchange и право публикации не подменять текстовой проверкой.
