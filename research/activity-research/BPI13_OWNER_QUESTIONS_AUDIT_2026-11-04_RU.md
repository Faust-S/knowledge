## 3. Что показывает зарегистрированный log

В реальном GitHub Actions на входе **819 случаев, 2351 зарегистрированное событие**, использован original pinned U1 на детерминированной выборке из **12 случаев / 50 событий**. Простая и воспроизводимая baseline-операция по **всему** файлу Open Problems нашла **284 шаблона activity-label A–B–A** в пределах случая после упорядочивания по заявленному timestamp.

Этот счётчик намеренно НЕ называется «ping-pong» команд: A и B — названия событий, а не идентификаторы исполнителей/групп. Нельзя также считать частоту A–B–A числом нарушений, циклов реальной работы, ошибочных поручений или долей задач. Не привязывать вывод к истинной хронологии вне зарегистрированного timestamp.

**Контрольная запись GitHub Actions:** `BPI13_OWNER_QUESTIONS 4 questions 819 cases 2351 registered events accepted_tasks 0 activity_patterns 284`; `BPI13_PUBLISHED_OWNER_QUESTIONS_SCOPED_PASS 4 published questions 819 reported cases 284 registered-label A-B-A motifs (NOT team ping-pong)`.

## 5. Почему это важно для общей IWXA

Эксперимент показывает узкий, но реальный участок будущего Activity Discovery: из недостаточно формализованной проблемы можно извлечь **подтверждённый предмет исследования**, проверить, какими доступными свидетельствами его можно поддержать и где данные явно недостаточны.

Это не самостоятельный Activity Engine и не доказательство точного выявления человеческих задач. Дальнейшая модель должна различать:

`PUBLISHED_OWNER_QUESTION → PROPOSED_INVESTIGATION → AVAILABLE_SOURCE_SCOPE → TESTABLE_HYPOTHESIS/UNKNOWN → REQUEST_FOR_INDEPENDENT_EVIDENCE → TASK_DECISION`.

В существующей архитектуре `research/task-discovery/` отвечает за квалификацию самостоятельных задач и экспертизу E5, `research/cross-lab/` — за поиск контекста/зависимости источников, исходный `Faust-S/iwxa` — за owner U1/T0/T1/Context Compiler, а Personal Agent — за реальные Task/Result. Ни один из этих owners в данном эксперименте не изменён.

## 6. Научные ограничения и следующий эксперимент

**Не подтверждено:** доступ к официальному 4TU оригиналу; licence audit; подтверждение фактической работы; независимая разметка задач; пригодность открытых проблем для всех четырёх вопросов; причинная зависимость между зарегистрированными событиями и рабочими ошибками; пользовательская польза. Отсутствующие данные не лечатся промптами.

**Следующий кандидат:** подключить к той же опубликованной постановке задач второй официальный журнал *incidents* (доступность/права/точная версия прежде всего), рассмотреть только те вопросы, где он действительно несёт нужные поля. Альтернатива — исследовать организационные атрибуты Open Problems, **если** они проверяемо присутствуют; не фантазировать их из label. Сравнить Task Investigation Extraction в `source-first` и `catalogue-prior` при одинаковых данных, фиксируя число неверно «доказанных» задач и стоимость уточнения.

Эта программа научно полезнее дальнейшего раздувания числа синтетических мутаций без новых независимых реальных данных.
