# Bypass Manager 0.3 Alpha: приватность, DNS и концепция прокси

**Статус:** анализ + пассивная диагностика Windows. Ни встроенного прокси, ни DNS-фильтра, ни модификации браузера сейчас нет. Никакой тест не доказывает полную анонимность пользователя.

## 1. Что защищает каждый компонент

| Механизм | Помогает | Не гарантирует |
|---|---|---|
| Отдельный VPN-клиент Amnezia | Шифрование пути от устройства до VPN-сервера, изменение адреса для трафика через туннель | Отсутствие IPv6/DNS/WebRTC-утечек, неидентифицируемость по аккаунтам |
| Bypass Manager + оригинальный winws2 | Локальная адресная DPI-обработка *внешнего* потока VPN; измерение успешности IPv4-пути | Шифрование само по себе, анонимность, работоспособность без совместимого VPN-сервера |
| Браузерная защита от трекеров | Межсайтовое отслеживание через cookies, трекеры и часть fingerprinting | Защиту от входа в личные аккаунты, всех вариантов fingerprinting |
| Независимый прокси после VPN | Отдельный выходной адрес для выбранных приложений, разделение информации между двумя операторами | Дополнительное шифрование через обычный SOCKS5, защиту от браузерного WebRTC обхода |

## 2. Почему IPv6 требует собственной проверки

IPv4 и IPv6 имеют разные маршруты. VPN с работающим IPv4 не обязан направлять IPv6 в туннель. При сравнении до/после подключения совпадающий публичный IPv6 по нескольким HTTPS-источникам отмечается `POSSIBLE_IPV6_BYPASS`. Ошибка сети, отсутствие IPv6 или изменение адреса не дают заключения об отсутствии утечек.

Важно: описание ограничения IPv6 в документации Amnezia относится к раздельному туннелированию и не заменяет проверку конкретного продукта/конфигурации. Программа не должна автоматически отключать IPv6 во всей Windows: это может нарушить связь с локальными устройствами и другими приложениями.

Источник: https://docs.amnezia.org/documentation/instructions/vpn-split-tunneling/

## 3. DNS: конфигурация не равна фактическому запросу

С Windows 10/11 приложение может определять настроенные DNS-серверы интерфейсов (`Get-DnsClientServerAddress`) и текущие маршруты (`Find-NetRoute`). `Get-DnsExposure.ps1` делает это **без DNS-запросов и без изменения настроек**. В локальную память и обезличенный JSON возвращаются только агрегированные счётчики, не адреса DNS-серверов и не имена адаптеров.

- `POSSIBLE_DNS_OUTSIDE_VPN` означает: Windows знает DNS-адрес с маршрутом вне названного VPN-интерфейса. Это **потенциальная возможность** утечки, а не перехваченный DNS-запрос.
- `DNS_ROUTE_INCOMPLETE` означает: часть маршрутов не определена либо список ограничен; заключение невозможно.
- `DNS_ROUTE_CHECK_UNAVAILABLE` означает: диагностика не выполнена.
- `DNS_ROUTES_OBSERVED` означает только наблюдаемые маршруты в момент проверки. **Не означает** `DNS_LEAK_FREE`.

Пример ситуаций, которые пассивная диагностика не раскрывает: собственный DNS-over-HTTPS браузера; DNS-over-TLS приложения; DNS-кэш; split tunneling по отдельным приложениям; NRPT; утечки при падении VPN или после смены сети. Для доказательства фактического DNS-выхода нужны отдельные контролируемые DNS-запросы и наблюдение пакетов/ETW на физическом и VPN-интерфейсах. Это задача будущей Windows-квалификации, не имитационный тест.

Microsoft: https://learn.microsoft.com/en-us/powershell/module/dnsclient/get-dnsclientserveraddress

## 4. Браузер: WebRTC, cookies, fingerprint

WebRTC может создавать прямые UDP-соединения и в некоторых конфигурациях обходить прокси, даже когда обычные HTTPS-запросы идут через прокси. Действия: использовать отдельный браузерный профиль для приватной работы; защиту от межсайтовых cookies и трекеров; сверить WebRTC/ICE-адреса с VPN-маршрутом. Отключение WebRTC может нарушить видеосвязь, поэтому должно быть выбором пользователя, а не системной правкой Bypass Manager.

Firefox предлагает Enhanced Tracking Protection и Total Cookie Protection; DoH Max Protection минимизирует возможность прозрачного возврата к системному DNS, но переносит доверие к выбранному DNS-провайдеру. Скрыть IP недостаточно, если авторизоваться в привычной учётной записи или оставить идентичный браузерный профиль.

Источники: https://www.rfc-editor.org/rfc/rfc8828.html ; https://support.mozilla.org/en-US/kb/enhanced-tracking-protection-firefox-desktop ; https://support.mozilla.org/en-US/kb/dns-over-https

## 5. «Матрёшка» VPN + прокси: решение для обсуждения

**A. Приложение -> VPN -> прокси -> сайт.** Выбирается только для приложений, которые умеют пользоваться прокси. ISP видит исходный VPN-транспорт, VPN-провайдер видит связь с прокси, прокси знает назначения, посещаемый сайт видит адрес прокси. Обычный SOCKS5 не даёт шифрования между VPN-сервером и прокси, если оно не предоставляется приложением. В этом режиме прокси не заменяет наш DPI-профиль, но может менять выходной IP. Понадобятся аутентификация, проверка доменных запросов на стороне прокси, проверки WebRTC и измерение реального egress.

**B. Приложение -> прокси -> VPN -> сайт.** Помогает скрыть адрес VPN-сервера от локальной сети лишь при реализации поддерживаемого способа подключения VPN через прокси. Обычный браузерный HTTP CONNECT не проксирует произвольный UDP AmneziaWG. Придётся выбирать серверный транспорт, для которого есть штатная поддержка внешнего прокси, либо специальный CONNECT-UDP с совместимым сервером. Это уже функция VPN-клиента/его транспорта, а не локального DPI-менеджера.

**C. Два последовательных VPN.** Два маршрутизирующих слоя увеличивают задержку, делают DPI и диагностику отказов менее предсказуемыми, усложняют DNS и не гарантируют независимости операторов. Не приоритет.

Прокси должен быть отдельным **необязательным** режимом. Не следует автоматически изменять Windows Proxy, WinHTTP, PAC, DNS, Firefox/Chrome, таблицы маршрутов или управлять Amnezia. Не следует использовать открытые чужие прокси или обещать анонимность через два узла.

**Предлагаемый следующий эксперимент:** на самостоятельно управляемом HTTPS-прокси с аутентификацией подтвердить для одного тестового браузера одновременно: HTTP CONNECT по защищённому каналу, выходной IPv4/IPv6, DNS-resolution на нужной стороне, поведение WebRTC, скорости и отказ без прямого fallback. Только после совместимого E2E-теста обсуждать интеграцию кнопки «Прокси после VPN». Источник стандартов для будущего UDP-проксирования: https://www.rfc-editor.org/rfc/rfc9298.html

## 6. Текущий предел испытаний

Linux unit/race и Windows CI могут подтвердить корректность диагностических функций, Win32 UI, PowerShell и winws2 dry-run. Они **не проверяют** настоящие DNS-пакеты пользователя, прохождение трафика через отдельную Amnezia и стабильность обхода DPI в чужой сети. Не сохраняйте публично `settings.json`, сырые сетевые дампы и журналы VPN-движка.
