# Bypass Manager: пересмотр продукта и архитектуры

**20 ноября 2026.** Решение по итогам пользовательских испытаний Windows Alpha 0.3 и исследования существующих механизмов. **Статус: новая продуктовая постановка, не реализованная сборка.**

## 1. Исправление исходной ошибки

Программа должна не обслуживать отдельный VPN-клиент, а **самостоятельно находить и поддерживать работающий доступ к интернету**. Прежняя Alpha 0.3 — техническая лаборатория диагностики VPN и отдельных DPI-фильтров. Её не следует выдавать за готовый продукт. GitHub Actions и моделирование не подтверждают работу на реальной сети владельца.

Основной сценарий: установить продукт один раз, включить его одной кнопкой, затем поддерживать работоспособность соединений автоматически, пока пользователь не выключит. Никакой обязательной зависимости от Amnezia Premium, ручного перебора восьми профилей, ввода IP серверов, циклического переключения работоспособного VPN ради теста.

## 2. Три действия интерфейса

1. **Включить / Выключить** — основное управление в одном месте. Должно запускать сам механизм, а не форму диагностики; после выхода из окна работа может продолжаться в фоне, если пользователь это включил при установке. Один активный маршрут и ясное текущее состояние.
2. **Скорость и регион** — по требованию измерить скорость, задержку, внешний IPv4/IPv6 и предполагаемую географию выхода, ASN/провайдера; показать время, источник и **какой именно путь** измерялся. Для браузера или конкретного приложения требуется отдельное свидетельство, нельзя приписывать ему IP проверяющей программы.
3. **Отчёт** — текущее состояние, выполненные действия, успешные/неуспешные попытки и причины. Подробный технический журнал только по запросу, а не на главном экране.

На главном экране обязательны короткие статусы: `Выключено`, `Подбираю соединение`, `Работает: прямой`, `Работает: локальная DPI-обработка`, `Работает: прокси/туннель`, `Частично работает`, `Не удалось восстановить`. Нельзя написать `Работает` лишь по наличию интерфейса или процессу фильтра.

## 3. Способы соединения, без привязки к бренду

### A. Прямое соединение без VPN — первая рабочая ступень

Существующая сеть, обычное приложение и обычный HTTPS/QUIC. HTTPS обычно уже зашифрован **самим сайтом/приложением**. Движок может менять сетевое представление части запросов для преодоления некоторых DPI-ограничений. Не следует описывать это как собственный VPN или дополнительное сквозное шифрование.

Повторно использовать **существующий оригинальный `winws2`/WinDivert**, но не ограничивать фильтр адресом сервера Amnezia. Для поддерживаемых протоколов есть фильтрация по портам, L7, hostlist и управляемым стратегиям `zapret2`. Начинать адресно с проверяемых проблемных сервисов/классов трафика, а не с глобальной модификации всех пакетов. Остановленный процесс должен прекращать все собственные изменения. Установка драйвера, права и устойчивое восстановление — отдельные технические требования этой ступени.

Дополнительный **локальный пользовательский SOCKS-режим** может быть реализован с уже существующим ByeDPI (MIT), прежде всего для браузеров и совместимого софта; он не является прозрачным системным VPN. Решение о включении отдельного движка принимается после технического сравнения с `winws2`, без параллельного собственного сетевого ядра.

### B. Прокси/удалённый туннель — только когда требуется

Если прямой путь недоступен из-за IP-маршрутизации/полной блокировки, локальной модификации недостаточно. Нужен доступный **удалённый** endpoint: HTTP(S)/SOCKS proxy, VPN, иной поддерживаемый транспорт. Стратегии умеют выбирать из **реально настроенных** пользователем подключений; не могут восстановить недоступный сервер из воздуха. Amnezia, Xray/VLESS и другие клиенты — потенциальные адаптеры, но не обязательная инфраструктура продукта. Профили или доступы вводятся только один раз, если этот режим вообще нужен. Не использовать неподдерживаемое тайное управление Premium либо серверные IP из догадок.

Должен быть режим работы с имеющимся прокси в браузере и в приложениях; системный VPN/TUN для всей ОС — отдельная опция после реального подтверждения. При пропаже всех серверов программа сообщает о таком ограничении и продолжает проверять прямые возможности.

### C. Браузерная версия

**Обычная веб-страница/PWA не может изменять произвольные системные TCP/UDP-пакеты, управлять Windows-драйвером или подключать чужие Windows-программы.** Браузерное расширение может управлять прокси-политикой **своего браузера**. Для запуска системной обработки расширению нужен установленный локальный исполняемый компонент через Native Messaging либо локальный интерфейс с контролем доступа.

Решение: сначала нативный Windows-движок с возможностью невидимого фонового режима. Затем, если оправдано продуктово, браузерное расширение/панель может пользоваться тем же процессом. Не разрабатывать второй сетевой движок ради веб-интерфейса.

## 4. Автоматический управляющий цикл

`Включить` -> измерить фактическую доступность целевых HTTPS-сервисов **без вмешательства** -> если всё работает, оставить прямой маршрут -> при признаках DPI-отказа испытать короткую **обратимую локальную обработку** выбранных соединений -> подтвердить конкретный успешный запрос/приложение -> включить найденную подходящую стратегию -> продолжать наблюдение и восстановление.

При отсутствии эффекта от локальной обработки и наличии заранее настроенного удалённого подключения — проверить его доступность и использовать только реально работающий endpoint; не переключать бездоказательно из одного недоступного сервера на другой. При ухудшении или конфликте вернуть прежний способ. События типа `Сервер недоступен`, `DPI не помог`, `Нарушен DNS`, `Неподходящий прокси`, `Подключение восстановлено`, `Нет доступного пути` различать в отчёте.

Нужны ограниченные по времени попытки, cooldown, память об успешном профиле **для данной сети/целей**, реакция на смену сети и остановка всех принадлежащих программе процессов при выключении. Не строить длительные A/B/A как обязательную преграду обычному доступу: они нужны для квалификации, а при работе достаточно кратких реальных сравнений и мониторинга.

В режимах, где пользователь требует обязательного скрытия IP, аварийный переход на прямой маршрут без его разрешения недопустим. Это единое первоначальное предпочтение, не серия всплывающих вопросов.

## 5. Что переиспользовать и что прекратить

**Сохранить:** исходный `winws2`, проверенную поставку компонентов, остановку своего процесса/rollback, тесты HTTPS и скорости, внешний IP, анализ Windows-сокетов, обезличенные отчёты, оценку A/B/A как вспомогательную, независимый CI и моделирование.

**Переработать:** 
- `manager.go`: от единичного внешнего endpoint и вручную выбранного DPI-профиля к прямой обратимой обработке **целевого трафика** и статусу реального соединения.
- `guide_windows.go` и `guide_plan.go`: перестать использовать AmneziaWG/VLESS и восемь вариантов как главный маршрут; новое автоматическое управление является **основным** действием пользователя.
- `product_ui_windows.go` и `gui_windows.go`: три действия, краткая текущая оценка, техническая панель спрятана от обычного пользователя; без потери возможности остановить обработку.
- `live_windows.go`, `proxy_path.go`, `app_routes*.go`: указание активного режима и области наблюдения, отсутствие ложного заключения об IP конкретного приложения.

**Запретить как продуктовые практики:** утверждать об успехе VPN по адаптеру, объявлять эффект DPI из одного CDN/фиктивной скорости, запускать фильтр с неподтверждённым endpoint, бесконечно запускать диагностический мастер, путать HTTPS данной программы с доступностью иных приложений, выпускать новую Windows Alpha только по мокам.

## 6. Последовательность реализации и приёмка

### Шаг 1. Реальное прямое подключение с локальной адаптацией (приоритет №1)

Собрать **запускаемый** продуктовый путь **без установленной Amnezia**: пользователь нажимает «Включить», продукт обнаруживает недоступный реальный HTTPS-ресурс, кратковременно включает выбранную стратегию `winws2` для его трафика, повторно запрашивает **тот же ресурс**, подтверждает успешное получение, оставляет обработку только при наличии улучшения. По «Выключить» очищается только собственный фильтр, исходная связь работает по-прежнему. Если сайт не удалось восстановить, статус честно сообщает об этом. Проверить установленную Windows-программу на независимой машине, права доступа, холодный перезапуск и откат.

### Шаг 2. Настоящий автоматический выбор и устойчивость

Несколько существующих профилей DPI под одной кнопкой, ограниченный перебор по типу сбоя, память работающего пути, watchdog, наблюдение без лишних диагностических окон; реальные тесты нескольких сетей и провайдерских блокировок. Не оптимизировать метрики при отсутствии проверенного доступа.

### Шаг 3. Подключение внешнего узла при необходимости

Универсальный ввод/импорт настроенного прокси/туннеля и переключение при отсутствии прямого доступа; существующий Amnezia может быть **необязательной** интеграцией. Подключение только при поддерживаемом интерфейсе и настроенных учётных данных. Не включать неработающий VPN для того, чтобы «проверить» DPI.

### Шаг 4. Браузер и отдельные программы

Опциональное расширение для поддерживаемых браузеров, адресный выбор прокси, независимое подтверждение выхода браузера, затем инженерная квалификация системных приложений и прозрачного перенаправления в Windows. Проводить отдельные тесты TCP, UDP/QUIC и реальные видео/голосовые сессии.

### Шаг 5. Финальный UX и подтверждение

Один компактный экран, фоновые обновления, «Скорость и регион», «Отчёт», запуск/остановка за одно действие; реальные скриншоты установленного продукта. Предъявлять два разных свидетельства: **прошла автоматическая модель** и **фактически исправлена работа конкретной программы/сайта на Windows**. Только второе позволяет принять функциональность.

## 7. Технические источники и критерии выбора компонентов

- zapret2/winws2, оригинальная документация: https://github.com/bol-van/zapret2/blob/master/docs/readme.md (существуют hostlist, L7-фильтрация и прямые TLS/HTTP/QUIC-стратегии; не требуется фиксированный адрес Amnezia).
- ByeDPI: https://github.com/hufrea/byedpi (локальный SOCKS-прокси, лицензия MIT; для системного перенаправления всех приложений сам по себе недостаточен).
- Microsoft WFP: https://learn.microsoft.com/en-us/windows/win32/fwp/about-windows-filtering-platform (системный контроль на уровне Windows, не доступен обычной странице браузера).
- Chrome extension proxy: https://developer.chrome.com/docs/extensions/reference/api/proxy (параметры прокси браузера).
- Chrome Native Messaging: https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging (связь расширения с установленным native host).
- Amnezia Local Proxy: https://docs.amnezia.org/documentation/instructions/local-proxy/ (это отдельный режим; недоступность её Premium-сервера не должна блокировать прямую обработку продукта).
- Amnezia conflicting apps: https://docs.amnezia.org/ru/troubleshooting/conflicting-apps/ (локальная DPI-обработка может конфликтовать с VPN; контроллер должен не слепо объединять все механизмы).

**Ни один из пунктов реализации выше не подтверждён этой запиской как готовая функция.** Следующее изменение кода — не дополнительный отчёт или симуляция, а работоспособное первое действие локальной DPI-обработки без VPN с реальными Windows-проверками.
